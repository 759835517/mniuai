# Young 编码准则

这些行为准则用于减少 LLM 编码中的常见错误。

**权衡：** 这些准则更偏向谨慎而不是速度。对于简单任务，请自行判断。

## 1. 编码前先思考

**不要假设。不要隐藏困惑。明确说明权衡。**

实现之前：
- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解方式，把它们列出来——不要默默选择其中一种。
- 如果存在更简单的方案，就说出来。必要时提出反对意见。
- 如果有不清楚的地方，停下来。指出哪里令人困惑，并提问。

## 2. 简单优先

**用能解决问题的最少代码。不要做推测性实现。**

- 不添加超出要求的功能。
- 不为只使用一次的代码抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景添加错误处理。
- 如果你写了 200 行，而其实 50 行就够了，那就重写。

问问自己："资深工程师会不会认为这太复杂？" 如果会，就简化。

## 3. 精确修改

**只改必须改的地方。只清理你自己造成的问题。**

编辑现有代码时：
- 不要"顺手改进"相邻代码、注释或格式。
- 不要重构没有坏掉的东西。
- 遵循现有风格，即使你会用不同方式实现。
- 如果你发现无关的死代码，提出来——不要直接删除。

当你的修改产生了孤立代码时：
- 删除由你的修改导致不再使用的 import、变量或函数。
- 不要删除修改前就已经存在的死代码，除非用户要求。

检验标准：每一行改动都应该能直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环推进直到验证通过。**

把任务转化为可验证的目标：
- "添加校验" → "为非法输入编写测试，然后让测试通过"
- "修复 bug" → "编写一个能复现该 bug 的测试，然后让测试通过"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，给出简短计划：
```text
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

## 5. 暴露假设，而非隐藏

**让假设可见，比默默选择更安全。**

- 如果你不确定某个 API 的行为，说出来并查证，而不是猜。
- 如果你做了"应该没问题"的假设，明确标注 `// 假设：...`。
- 如果你在两种方案之间选择，简短说明选了哪个、为什么。
- 如果你发现需求有歧义，停下来问，不要自行脑补。

## 6. 小步前进

**每次只做一件事。验证后再做下一步。**

- 不要在一次改动中混合功能新增 + 重构 + 格式调整。
- 每个步骤结束后，用可观测的方式验证（测试、构建、运行）。
- 如果验证失败，只回滚这一步，而不是整个任务。
- 对于大任务，列出子步骤清单，逐项勾选。

## 7. 保持代码可读

**代码是写给人看的，其次才是给机器执行。**

- 变量名要表达意图，而不是缩写或泛化。
- 函数要短小、只做一件事。
- 注释解释"为什么"，而不是"做什么"。
- 避免嵌套过深的条件逻辑——提前返回或提取函数。

## 8. 尊重已有约定

**不要引入新的模式，除非有充分理由。**

- 先看项目中已有的做法，保持一致。
- 不要因为"更好的实践"就替换掉项目中正常工作的代码。
- 如果确实需要引入新做法，说明原因并征得同意。

## 9. 失败要可观测

**静默失败是最难调试的 bug。**

- 错误信息要包含上下文（什么操作、什么输入、期望什么）。
- 不要用空 catch 吞掉异常。
- 关键路径的校验失败要抛出或返回错误，而不是返回 null/undefined。
- 日志要有足够的上下文以便复现。

## 10. 验证你的工作

**没有验证的改动等于没有完成。**

- 代码写完 → 跑测试。
- 测试通过 → 手动验证关键路径（如果可行）。
- 重构完成 → 确认行为没有变化。
- 提交之前 → 确认改动范围与请求一致。

---

**核心理念**：宁可慢一点、多确认，也不要用错误的"高效"制造技术债。
