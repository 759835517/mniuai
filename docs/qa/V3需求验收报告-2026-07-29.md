## 二、Blocker（阻断核心流程）

### B1：admin-app 零实现，阶段一目标未达成

**问题**：V3 阶段一（0-3 个月）明确要求 admin-app CMS 后台上线，支持多端内容发布。实际状态：`apps/admin-app/` 下无 `src/app/` 目录，没有任何页面，无法启动为可访问站点。

**影响**：课程、文章、用户数据无法通过管理界面操作，内容运营工作全部阻塞。

**端口偏差**：V3 要求 admin 用 3006，实际 package.json 配置的是 3002（与 V3 的 kids-app 端口冲突）。

**验收标准**：admin-app 至少具备：课程 CRUD、文章 CRUD、用户查看、RAG 知识库管理（已有 `/api/v1/admin/rag` 接口）。

---

### B2：kids-app 零实现，端口冲突

**问题**：`apps/kids-app/` 下无 `src/app/` 目录，无任何页面，无法启动。

**额外问题**：kids-app 的 `package.json` 端口配置为 3001，与 engineer-app 完全相同——两端无法同时启动。V3 要求 kids 用 3002。

**影响**：少儿端完全不可访问，对赌承诺（竞赛获奖退款）无从落实。

---

### B3：职场赋能端 PRD 定位与 V3 需求背道而驰

**问题**：这是本次验收最严重的架构级偏差。

V3.0 明确规定 `pro.mniuai.com` 的目标用户和四个功能模块：

| V3 模块 | 目标用户 | V3 要求的功能点（各 5 项） |
|---|---|---|
| A 自媒体/内容运营 | 抖音/小红书/B站创作者 | 爆款标题生成器、视频脚本、封面文案+配图提示词、热点选题（接热搜API）、数据复盘 |
| B 公众号运营 | 公众号运营者 | AI写文章、排版优化、月计划系列内容、评论回复模板、历史数据分析 |
| C 门店小老板获客 | 餐饮/美妆/教育行业老板 | 朋友圈文案（按行业分）、活动策划助手、话术库、本地化推广、视频号内容 |
| D 学校/机构简讯 | 学校运营、机构招生 | 活动推文、正式公文、家校周报、荣誉通报、招生简章 |

**实际 PRD（docs/prd/职场赋能端-pro.mniuai.com-PRD.md）的定位**：产品经理、运营经理、市场专员、HR——这是完全不同的用户群，对应的是通用职场效率工具。

**实际实现的 6 个工具**：AI 文档写作（PRD/报告/邮件）、数据分析（Excel 式）、会议纪要、简历优化、汇报材料、职场模板库。

对 V3 四模块 20 个功能关键词（爆款标题、视频脚本、抖音、小红书、公众号、朋友圈、门店、话术、招生、荣誉通报等）在整个 pro-app 源码中**零命中**。

**结论**：pro-app 的 PRD 和实现是一套完整但与 V3 无关的产品。需要在产品层面明确：
- 选项 A：接受当前实现，更新 V3 需求文档将 pro 定位改为"职场通用效率"
- 选项 B：按 V3 重新设计 pro-app，替换当前所有工具

## 三、Critical（导致业务价值失真）

### C1：edu-app 课件导出是 .txt 而非 .pptx，文案误导用户

**位置**：`apps/edu-app/src/app/tools/slides/page.tsx:65`

**现象**：页面文案写"一键生成可下载的 PPTX 课件"，但实际下载逻辑：

```js
const blob = new Blob([text], { type: "text/plain;charset=utf-8" });
a.download = `${form.topic}-课件.txt`;
```

产出的是纯文本幻灯片大纲，文件扩展名 `.txt`，不是 `.pptx`。

**影响**：用户看到"下载 PPTX"点击后拿到的是 txt 文件，功能承诺与实现不符，直接损害信任。

---

### C2：edu-app 作业批改无图片上传，与 V3 描述的视觉模型能力不符

**问题**：V3 要求"上传作业图片，AI 给出批改建议（视觉+语言模型）"。实际 `/tools/grade/page.tsx` 三个输入全是 `<textarea>`（题目、学生答案、参考答案），无任何 `<input type="file">` 或图片上传能力，调用的是 `eduApi.gradeSubmission({subject, question, studentAnswer, standardAnswer})`。

**影响**：现实场景中教师的作业是纸质或图片形式，纯文本输入要求教师手动转录，不符合"减负增效"定位。

---

### C3：edu-app 学生简讯生成模块完全缺失

**问题**：V3 明确要求"输入班级活动，生成学校推文/家长通知（图文生成）"。edu-app 11 个页面中无此功能，`/templates` 有部分家长会通知模板，但仅是静态文本卡片，无 AI 生成能力。

**影响**：V3 六大功能模块中少一个，付费用户的核心场景之一无法使用。

---

### C4：campus-app 对赌门槛偏离 V3，作品集指标被替换为刷题指标

**问题**：V3 的大学生端对赌核心条件之一是"完成至少 3 个作品集项目"——这是证明就业能力的核心物证。实际 `apps/campus-app/src/app/my/guarantee/page.tsx` 中，作品集指标被替换为两项刷题指标（完成编程练习 ≥200 题、通过 ≥120 题），`/portfolio/[username]` 页面有展示作品集能力，但作品集数量未纳入对赌门槛计算。

**影响**：刷题数量与找到工作的因果关系远弱于作品集——对赌兜底条件对用户的就业帮助较低，影响产品差异化价值。

---

### C5：后端 campus/edu/pro 三模块无任何测试

**问题**：17 个测试文件覆盖的模块不包含 campus、edu、pro。pro 和 edu 模块有 API 外壳但无持久化，实现中有多处 `TODO: 持久化` 注释（保证申请、用量记录等接口直接返回成功而不写入数据库）。

**影响**：pro 和 edu 的对赌申请、工具使用次数等关键数据无持久化意味着数据丢失，用户满足退款条件时可能无法举证。

---

## 四、Major（影响用户价值）

### M1：campus 四阶段学习路径未实现

V3 要求四阶段路径（AI工具上手 → 方向深入 → 求职冲刺 → 就业陪跑），实际 `/paths` 按职业方向划分（全栈/前端/Java后端/数据分析），不是学习阶段模型。对用户来说缺少"从零到就业"的进度感知。

### M2：campus 无就业状态追踪字段

对赌退款触发条件是"180 天内未就业"，但后端 campus 模块和前端均无就业状态字段或申报入口。用户到期后无法通过平台主张退款权利。

### M3：后端 /api/v1/common/** 前缀完全不存在

V3 设计中三端共享能力（视频、文章、考试、成长）应走 `/api/v1/common/**`，实际路由是 `/api/v1/courses`、`/api/v1/articles`、`/api/v1/growth` 等旧路径，与 V3 架构设计不符，未来多端扩展时路由混乱。

### M4：后端 /api/v1/kids/** 完全不存在

kids 模块目录不存在，无任何 kids 相关后端能力。

### M5：edu-app 无数据库建表脚本，全量硬编码或 AI 直出

edu 模块无 migration SQL（campus 有 V15__campus_module.sql，pro 无，edu 无）。教师工具使用记录、备课历史等完全无持久化，`/my/history` 页面展示的数据无法保存。

### M6：engineer-app/edu-app/pro-app 的 E2E spec 无 playwright.config.ts

三端有 `tests/*.spec.ts` 但缺 `playwright.config.ts`，无法直接 `npx playwright test`。与 website 和 campus-app 的完整 E2E 配置不一致，无法纳入 CI 流水线。

### M7：edu 和 pro 的对赌申请接口是空实现

ProController 的 `POST /guarantee/apply` 和 EduController 的 `POST /guarantee/apply` 在代码中标注 `TODO: 持久化`，实际直接返回 200，不写数据库，承诺给用户的退款流程从申请阶段就是虚的。
